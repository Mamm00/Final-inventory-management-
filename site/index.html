What the app actually does

Nine views, one data model, and every piece of reference data editable from the interface — nothing is hard-coded, so a new warehouse or fabric never needs a code change.

Warehouses and shelves

Each shed carries the fabric types it is licensed for, and each of those a list of colours. Stock is always read as “this colour, in this fabric, in this shed” — never a loose number typed into a total.

Rolls, and the maths behind them

Opening rows, receipts, issues and movements add up to one number per combination, computed the same way in the table, the chart, the print sheet and the CSV. Metres fall out of meters-per-roll; nobody types them.

Issues, receipts, transfers

A movement is validated before it is written: enough stock at the source, the colour mapped at the destination, and the balance re-derived — never hand-edited.

An inventory you can walk

Stock Overview opens with one card per shed — fabric types, colours, rolls, grade mix. Open a card and you are inside it: fabric type, then its colours, then the roll count on the shelf.

Reports on letterhead

Every table prints with the company name and the mark in the header, in the language you are reading, sized for A4. Print-to-PDF is the only dependency.

Backups in and out

Full JSON backup and restore for the whole workspace, CSV export of every table — the colour codes, the stock overview, the ledger — no database to migrate.

Roles that hold

Each keeper has full control inside their own five sheds and a read-only window on the other keeper’s. They may add fabric types and colours to the shared catalogue, but never delete from it. Denials are explained on screen, and logged.

Audit trail

Writes, edits, deletions and blocked attempts are recorded with who, when and what — the log is a view in the app, not a buried console.

Deploy it on GitHub Pages in four commands

The site lives in site/ and is already static: commit it, point Pages at it, done. Nothing to install, nothing to build on the server.

Push the repository

From the project root, send site/ to a new GitHub repository.

Turn Pages on

Settings → Pages → “Deploy from a branch”, branch main, folder /site.

Or let Actions do it

The included workflow publishes site/ on every push — and fails if site/ is not what the sources build.

Open it

The landing page is at the root; the app is at ./app/index.html. Both also work from file://.

# 1 · first commit, from the project root
git init -b main
git add -A
git commit -m "Al Azhar Tex · fabric roll inventory + Pages site"

# 2 · create the repo on GitHub, then push it
git remote add origin https://github.com/OWNER/REPO.git
git push -u origin main

# 3 · Pages: Settings → Pages → Branch: main, folder: /site
#     (or keep the workflow below and skip the folder choice)

# 4 · rebuild the site from its sources before every release
python3 tools/build_site.py
python3 tools/build_site.py --check   # CI: fails if site/ is stale
Why .nojekyll is in the tree

It tells Pages to publish the files exactly as committed instead of running them through Jekyll. Nothing here needs Jekyll, and an empty file is what keeps that guarantee.

Deep links need the 404 trick

Pages has no rewrite rules, so 404.html reads the requested path and bounces the browser back to the app’s hash route. That is also why the app routes with #/… in the first place.

Who can do what

Permissions are per action, and warehouse-scoped where it matters. Colour codes are each keeper’s own list — the admin sees all of them. A denial says so on screen and writes an audit row.

What this is not

It is a client-side app: data lives in this browser’s local storage and the sign-in gates workflow, not traffic. Anyone with the file and the machine can read it. Treat Pages as distribution, not as a vault — put it on an internal host or behind SSO if that matters.

Two people, one warehouse

There is no server to arbitrate. The supported pattern is one browser per workstation plus JSON backups exchanged at the end of a shift — the export carries every table, and restoring replaces them.

Questions people ask before deploying

Does it need a server, a database or a build?

No. app/index.html is the whole application — markup, styles, script, artwork and icons inline. Opening it from a USB stick works the same as Pages, apart from the browser’s own storage being per-origin.

Where is the data kept?

In localStorage, autosaved on every change. Use Settings → Backup to write a JSON file out and to bring it back; that file is the migration path between browsers and machines.

Can we change the company name, the palette or the logo?

The name is one field in Settings and it flows to the sidebar, the tab title, the profile card, the in-app guide and the printed letterhead. The palette is two CSS variables. The artwork is generated from one table of measured numbers in tools/make_logo.py; regenerate and the app, the favicon, this page and the logo file all follow.

Is Arabic a real translation or a label swap?

Both directions are first-class: the document flips to right-to-left, tables reorder, arrows mirror, and printed reports come out in the language you are reading. Every string on both the app and this page goes through the same dictionary.

What happens when we add a warehouse next month?

You add it in the interface. It appears in every filter, dropdown, KPI, chart and export, and keepers can then be scoped to it. No redeploy is required — which is the point of keeping reference data out of the code.

Is it safe to put on GitHub Pages?

Only for what it is: a workflow gate, not a vault. Stock data lives in one browser's local storage, the passwords are checked in the page, and anyone holding the file and that machine can read it. Fine for a private repo behind your own GitHub sign-in, or for a USB stick; not fine for publishing real quantities to the open internet. If that changes, the app is the same file — point it at an internal host or a VPN.

Can my accountant open the export in Excel?

Yes. Every CSV is written as UTF-8 with a byte-order mark so Arabic names survive the double-click, fields containing commas or quotes are escaped properly, and values that start with = + - @ get an apostrophe so Excel will not try to evaluate them as formulas. JSON is the other export, and it is what restores the whole database on another machine.
